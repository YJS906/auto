# 확인한 사실과 남은 실측

## 자료·환경

- 실제 사용한 입력: `src/첫 번째 사진.jpg`, 트랙 ZIP에서 추출한 PNG/PDF/DXF/DWG. 별도 두 번째 트랙 사진은 작업 폴더에서 확인하지 못해 PNG를 비교 자료로 사용했습니다. 다른 ZIP과 PPTX는 수정하지 않았습니다.
- 사진: 네 바퀴 차체, LIMO PRO 표기, 상부 전방 브래킷의 여러 광학 창이 있는 장치, 전면 표시부와 비상정지 버튼 확인. 장치 모델·렌즈·정확한 각도·IMU/LiDAR 구성·주행 모드는 확인 불가.
- Ubuntu 24.04.4, ROS Jazzy, Gazebo Sim 8.15.0, ros_gz 1.0.24. 초기 NVIDIA RTX 4060 Mobile 드라이버 통신 실패 후 복구 완료: 커널 `7.0.0-34-generic`용 NVIDIA `595.99.02` DKMS 모듈 설치, RTX 4060 Ogre2 EGL 렌더링과 15개 런타임 검사 통과(`reports/nvidia/`). 이후 재부팅한 커널 `7.0.0-42-generic`에서도 GPU 인식과 추가 주행·센서 검사를 통과했습니다(`reports/extended/`). AMD 780M, Mesa 25.2.8에서도 초기 렌더링 시험 성공.
- 원래 워크스페이스에는 ROS package가 없었음. 현재 독립 `limo_autorace_sim` 패키지만 빌드.

## 도면

DXF에는 LINE 702, SPLINE 218, ARC 60, DIMENSION 85, INSERT 1개가 있습니다. `Visible` 형상은 333.333333 × 200 단위이며 개별 치수 재정의 `dimlfac=30`이 붙습니다. 전체 가로 치수 핸들 `4DE`는 10000 mm, 세로 `4EC`는 6000 mm입니다. PDF 수치와 일치합니다. 명목 차로 폭은 대표 구간 500 mm, 선 폭은 20/30/40 mm 등입니다.

INSERT는 `BORDER`의 `ISO_A2_SHEET`이고 translation=(0,0,0), scale=(1,1,1), rotation=0입니다. 실제 트랙 요소는 블록 안이 아닌 modelspace에 직접 있습니다. 도면 헤더 `$DIMLFAC=1`과 개별 요소 재정의 30이 다르므로 헤더만으로 축척을 정하지 않았습니다. DWG는 원본 보존만 했으며 별도 디코딩 교차검증은 미검증입니다. 실제 출력물의 가로·세로는 현장 실측이 필요합니다.

모든 도로 표시를 평면 텍스처로 생성했습니다. 중앙 분리 모양과 지그재그 선이 물리 구조물이라는 증거가 없어 높이·충돌을 만들지 않았습니다. CAD 폐곡선 중 넓은 영역과 다수 내부 구멍이 있는 횡단보도 사이 영역을 제외하는 규칙은 이 제공 도면에 맞게 검토한 것입니다. 다른 CAD를 넣을 때는 `reports/track_preview.png`를 다시 확인해야 합니다.

공식 `limo_ackerman.xacro`, `limo_four_diff.xacro`, `limo_steering_hinge.xacro`, `limo_ackerman.gazebo`와 드라이버를 검토했습니다. 공식 wheel/base DAE를 그대로 참조하고 Xacro의 바퀴-조향 링크 토폴로지를 재구성했습니다. 기존 Classic plugin 파일을 include하지 않습니다. 원본 조향 힌지에도 바퀴에 겹치는 collision이 있어 새 모델에서는 조향 힌지 collision을 없애고 바퀴 원통만 접지하게 했습니다.

DAE 원시 정점 범위: 차체 약 0.190×0.322×0.229 m, 바퀴 약 0.0963×0.0747×0.0963 m. 외관 메시와 공식 collision 값도 완전히 같지 않습니다. 메시의 전체 노드 변환을 포함한 실측 Pro 외형 인증값은 아니며 외관 참고로만 사용합니다.

구동은 `JointVelocityCmd`로 바퀴 회전 및 조향 속도를 주는 Harmonic 플러그인을 사용합니다. 차량 pose를 직접 바꾸지 않습니다. 명령 제한은 `command_guard`, 조향 응답 P gain은 Gazebo 플러그인, 마찰은 바퀴와 바닥 설정, slip compliance는 WheelSlip 플러그인에서 처리합니다. 이상적 속도 구동이므로 모터 전류·토크 포화·서스펜션·타이어 변형까지 식별한 모델은 아닙니다. URDF effort 값만으로 실제 모터 특성이 재현된다고 가정하지 마십시오.

## 실차 확인 목록

1. 현재 기계식 주행 모드와 driver에서 보고하는 motion mode 확인.
2. 하중 상태 휠베이스, 좌우 바퀴 중심 간 거리, 킹핀 간 거리, 바퀴 반지름, 차체 외곽·최저 지상고.
3. 배터리·센서를 포함한 총 질량, 무게중심 높이와 앞뒤 하중 배분.
4. 실제 좌우 조향 한계, 조향 명령 후 응답시간, 중앙/내측 조향각 환산.
5. 센서 모델·해상도·수평/수직 화각·distortion·CameraInfo, 후륜 중심 기준 센서 xyz/rpy.
6. 트랙 출력 실물 10×6 m 여부와 0.5 m 대표 차로 폭, 실제 도색 색상·물리 장애물 유무.
7. 실차 `/cmd_vel` 타입, topic names, `odom→base_link` 기준점, TF 발행 책임.

보정은 저속 직진으로 바퀴 반지름/속도 배율, 일정 속도·조향 원주행으로 실제 회전반경 R과 `δ=atan(L/R)`, 속도/조향 step 로그로 가감속·조향 응답을 맞춥니다. 독립 외부 위치 측정과 차량 encoder/IMU를 함께 기록해야 미끄러짐과 encoder 오차를 구분할 수 있습니다. 카메라는 체커보드 내부 보정과 지면 기준 외부 보정을 수행합니다.

공식 driver의 Ackermann callback에는 `linear.x/angular.z`와 좌·우 angle scale 사용을 포함한 코드가 있습니다. 현재 설치된 실차 driver가 같은 버전인지는 미확인이고, 0/0 입력 처리 등도 실차 전환 전에 검토해야 합니다. 이 작업에서는 실차 driver를 수정하지 않았습니다.

## 차동구동 추가 검증

차동모드에서 측면 미끄럼이 0이면 바퀴가 반대로 회전해도 차체가 돌지 않는 문제가 실제 시험에서 확인됐습니다. 마찰 방향을 바퀴 축에 맞추고 차동모드 측면 slip compliance를 `diff_lateral_slip: 1.0`으로 분리해 회전을 복구했습니다. 이 값은 실차 타이어·바닥에서 식별한 값이 아닙니다. 제자리 회전 3초 동안 명령은 0.6 rad/s였지만 실제 yaw 변화는 약 1.14 rad였으므로 구동 명령과 실제 차체 응답이 완전히 일치하는 모델로 취급하지 마십시오. 실차 원주행·제자리 회전 측정으로 추가 보정해야 합니다.
